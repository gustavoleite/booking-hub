# RFC-010: Padrão de Documentação OpenAPI para Autenticação Delegada (Gateway Offloading)

**Autor:**[Seu Nome/Sua Equipe]
**Data:** 29 de Março de 2026
**Status:** 🟢 Aprovada para Implementação
**Componentes Afetados:** Todos os Microsserviços Internos (`catalog-service`, `booking-service`, etc.)
**Stack:** Spring Boot 3.x, `springdoc-openapi-starter-webmvc-api`, Swagger UI

## 1. Sumário Executivo
Esta RFC propõe o padrão de configuração do **Swagger/OpenAPI** nos microsserviços internos do ecossistema *Beauty & Wellness*. O objetivo é mascarar parâmetros de controle interno (como `X-User-Id` e `X-User-Role` injetados pelo API Gateway) na documentação gerada e, ao mesmo tempo, instruir a interface gráfica (Swagger UI) a exibir o botão de Autenticação via **Bearer Token (JWT)**, refletindo a experiência real do cliente/Front-end.

## 2. Contexto e Motivação
Em nossa arquitetura, o **API Gateway** é responsável por interceptar o cabeçalho `Authorization: Bearer <token>`, validá-lo, decodificá-lo e repassar a identidade do usuário para os microsserviços através do cabeçalho `X-User-Id`.

Se o *springdoc-openapi* ler o código dos nossos *Controllers* de forma nativa, ele exigirá que o usuário preencha o campo `X-User-Id` manualmente na tela do Swagger, o que:
1. Confunde os desenvolvedores de Front-end (que devem enviar o Token, não o ID).
2. Expõe detalhes da infraestrutura interna na documentação pública.
3. Impossibilita o teste integrado via Swagger UI do Gateway.

## 3. Diretrizes de Implementação

Para resolver esse problema de *Developer Experience* (DX), aplicaremos duas configurações no código de cada microsserviço (ex: `catalog-service`).

### 3.1. Configuração Global de Segurança (O Botão "Authorize")
Criaremos uma classe de configuração centralizada para definir o esquema de segurança OpenAPI. Isso fará com que o Swagger UI renderize o botão verde "Authorize" no topo da página.

**Arquivo:** `infrastructure/configuration/OpenApiConfig.java`
```java
package br.com.beauty.catalog.infrastructure.configuration;

import io.swagger.v3.oas.annotations.OpenAPIDefinition;
import io.swagger.v3.oas.annotations.enums.SecuritySchemeType;
import io.swagger.v3.oas.annotations.info.Info;
import io.swagger.v3.oas.annotations.security.SecurityScheme;
import org.springframework.context.annotation.Configuration;

@Configuration
@OpenAPIDefinition(info = @Info(title = "Catalog Service API", version = "v1"))
@SecurityScheme(
    name = "bearerAuth", // Nome do esquema que será referenciado nos controllers
    type = SecuritySchemeType.HTTP,
    scheme = "bearer",
    bearerFormat = "JWT",
    description = "Insira o token JWT gerado pelo Auth Service."
)
public class OpenApiConfig {
}
```

### 3.2. Ocultação de Headers e Exigência de Segurança nos Controllers
Nos *Controllers* REST, usaremos duas anotações fundamentais:
* `@SecurityRequirement(name = "bearerAuth")`: Avisa ao Swagger que este endpoint (ou a classe inteira) exige o envio do token configurado acima.
* `@Parameter(hidden = true)`: Avisa ao Swagger para omitir o cabeçalho interno da interface gráfica e da geração do JSON base.

**Arquivo:** `infrastructure/adapters/in/rest/EstablishmentController.java`
```java
package br.com.beauty.catalog.infrastructure.adapters.in.rest;

import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.Parameter;
import io.swagger.v3.oas.annotations.security.SecurityRequirement;
import io.swagger.v3.oas.annotations.tags.Tag;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.UUID;

@RestController
@RequestMapping("/api/catalog/establishments")
@Tag(name = "1. Estabelecimentos", description = "Gestão de Salões (Requer ROLE_OWNER)")
public class EstablishmentController {

    @PostMapping
    @Operation(summary = "Criar um novo estabelecimento")
    @SecurityRequirement(name = "bearerAuth") // Exige o JWT no Swagger
    public ResponseEntity<Void> createEstablishment(
            // Oculta o parâmetro interno gerado pelo Gateway
            @Parameter(hidden = true) @RequestHeader("X-User-Id") UUID ownerId,
            @RequestBody CreateEstablishmentDTO dto) {
            
        // ... chamada para o UseCase (Clean Architecture)
        return ResponseEntity.status(201).build();
    }
}
```

## 4. Estratégia de Teste (Como os desenvolvedores usarão)

Com essa configuração, teremos dois fluxos claros de teste durante o desenvolvimento:

### Cenário A: Teste Integrado (Via API Gateway - Porta 8080) -> *Recomendado*
1. O desenvolvedor acessa `http://localhost:8080/swagger-ui.html`.
2. Seleciona a definição do `Catalog Service` no menu superior direito.
3. Clica em **Authorize** e insere o token JWT válido obtido no `Auth Service`.
4. Ao executar a requisição `POST /api/catalog/establishments`, o Swagger UI anexará automaticamente o header `Authorization: Bearer <token>`.
5. O Gateway interceptará, validará o JWT, removerá o cabeçalho original e injetará o `X-User-Id` transparente para o *Catalog Service*. **O fluxo ocorre de forma perfeita de ponta a ponta.**

### Cenário B: Teste Isolado / Debug (Via Postman no Catálogo - Porta 8083)
Caso o desenvolvedor não queira subir o Gateway e o Auth Service na máquina (para poupar memória ou focar apenas em testes do Catálogo):
1. O Swagger UI local (`http://localhost:8083/swagger-ui.html`) **não funcionará** para criar dados, pois ele enviará um Token Bearer que o Catálogo não sabe decifrar (ele espera `X-User-Id`).
2. O desenvolvedor deve abrir o **Postman**, apontar direto para a porta `8083` e forjar o cabeçalho manualmente:
    * Key: `X-User-Id`
    * Value: `123e4567-e89b-12d3-a456-426614174000` (Qualquer UUID válido de teste).
3. O microsserviço aceitará a requisição, permitindo o isolamento total para TDD/BDD.
