# RFC-006: Arquitetura e Modelagem de Domínio do Catalog Service

**Autor:**[Seu Nome/Sua Equipe]
**Data:** 25 de Março de 2026
**Status:** 🟡 Em Revisão (Aberto para Comentários)
**Componente:** Catalog Service
**Stack:** Java 21, Spring Boot, PostgreSQL, gRPC (Protobuf), RabbitMQ

## 1. Sumário Executivo
Esta RFC define a arquitetura do `Catalog Service`, responsável por gerenciar o domínio de Estabelecimentos (Salões), Profissionais e os Serviços prestados. O microsserviço atuará como a "fonte da verdade" estrutural do sistema, fornecendo as grades fixas de horários, preços e durações de serviços que serão consumidos pelo `Booking Service` (via gRPC) para o cálculo de disponibilidade de agendamentos.

## 2. Decisões de Negócio (Contexto)
Para refletir a realidade do mercado de beleza e bem-estar (gig economy/freelancers), o modelo foi desenhado sob as seguintes premissas aprovadas:
1. **Profissionais Independentes:** Um profissional pode trabalhar em mais de um estabelecimento (Relação N:N).
2. **Precificação e Duração Dinâmicas:** O preço de um serviço (ex: "Corte") e sua duração não são fixos no salão, mas sim atrelados ao vínculo do profissional com aquele salão (ex: Barbeiro Sênior cobra mais caro e faz mais rápido que o Júnior no mesmo salão).
3. **Separação de Responsabilidades:** O Catálogo armazena apenas a **Grade Fixa** de trabalho. A matemática de "horários livres em um dia específico" é responsabilidade do `Booking Service`.

## 3. Modelagem Tática (Domain-Driven Design)

O domínio será estruturado em duas Raízes de Agregado (Aggregate Roots) independentes, conectadas por uma Entidade de Vínculo.

### 3.1. Aggregate Root: `Establishment` (Estabelecimento)
Controlado pelo `ROLE_OWNER`.
*   **Identidade:** `EstablishmentId` (UUID)
*   **Atributos:** `name`, `cnpj`, `description`, `photos` (Lista de URLs).
*   **Value Objects:**
  *   `Address` (Rua, Número, CEP, `Latitude`, `Longitude`).
  *   `DefaultBusinessHours` (A grade mestre do salão. Ex: Seg-Sex 08:00 - 20:00).
*   **Entidades Internas:**
  *   `ProvidedService`: O catálogo de serviços base do salão (Sem preço. Apenas `id`, `title`, `description`).

### 3.2. Aggregate Root: `Professional` (Profissional)
Controlado pelo `ROLE_PROFESSIONAL` (Criado via evento quando o Auth Service registra um usuário com esta role).
*   **Identidade:** `ProfessionalId` (UUID - Mesmo ID do Auth Service).
*   **Atributos:** `name`, `bio`, `avatarUrl`.
*   **Value Objects:** `Specialties` (Lista de strings:["Cabelo", "Barba"]).

### 3.3. A Ligação Estratégica: `Affiliation` (Vínculo/Contrato)
Pertence ao agregado do `Establishment`. Representa o contrato de um profissional específico operando naquele salão.
*   **Identidade:** `AffiliationId` (UUID)
*   **Referências:** `professionalId`.
*   **Value Objects:**
  *   `WorkSchedule`: A grade fixa do profissional *neste* salão. **Invariante de Domínio:** O horário do profissional não pode ultrapassar o `DefaultBusinessHours` do salão.
*   **Entidades Internas:**
  *   `ServiceOffering`: Conecta um `ProvidedService` ao profissional. Define o `Price` (Money/BigDecimal) e a `Duration` (em minutos).

## 4. Modelagem de Dados (PostgreSQL)

O esquema relacional refletirá o modelo DDD com as seguintes tabelas e chaves estrangeiras:

*   **`tb_establishments`**: `id` (PK), `owner_id`, `name`, `lat`, `lng`, etc.
*   **`tb_business_hours`**: `id` (PK), `establishment_id` (FK), `day_of_week`, `open_time`, `close_time`.
*   **`tb_provided_services`**: `id` (PK), `establishment_id` (FK), `title`.
*   **`tb_professionals`**: `id` (PK), `name`, `bio`.
*   **`tb_affiliations`**: `id` (PK), `establishment_id` (FK), `professional_id` (FK), `active` (BOOLEAN).
*   **`tb_work_schedules`**: `id` (PK), `affiliation_id` (FK), `day_of_week`, `start_time`, `end_time`.
*   **`tb_service_offerings`**: `id` (PK), `affiliation_id` (FK), `service_id` (FK), `price` (DECIMAL), `duration_minutes` (INT).

## 5. Contratos de Comunicação

### 5.1. APIs RESTful (Para o Gateway / Clientes)
*   `POST /api/catalog/establishments` (Cria salão - *Apenas OWNER*)
*   `GET /api/catalog/establishments/{id}` (Detalhes públicos do salão)
*   `POST /api/catalog/establishments/{id}/affiliations` (Adiciona um profissional ao salão, definindo sua grade e preços - *Apenas OWNER*)

### 5.2. Contrato gRPC (Comunicação Síncrona Interna)
O `Booking Service` chamará o `Catalog Service` via gRPC no exato momento que um cliente quiser ver os horários livres ou confirmar um agendamento.

**Arquivo: `catalog_service.proto`**
```protobuf
syntax = "proto3";
package br.com.beauty.catalog.grpc;

service CatalogGrpcService {
  // Retorna a grade de horários e os detalhes do serviço para o cálculo do Booking
  rpc GetProfessionalSchedule (ScheduleRequest) returns (ScheduleResponse);
}

message ScheduleRequest {
  string establishment_id = 1;
  string professional_id = 2;
  string service_id = 3;
}

message ScheduleResponse {
  bool is_active = 1;
  double price = 2;
  int32 duration_minutes = 3;
  repeated DaySchedule fixed_schedule = 4;
}

message DaySchedule {
  int32 day_of_week = 1; // 1 (Segunda) a 7 (Domingo)
  string start_time = 2; // "09:00"
  string end_time = 3;   // "18:00"
}
```
*Por que gRPC aqui?* Porque o Booking Service fará essa pergunta milhares de vezes por minuto. O gRPC (Protobuf sobre HTTP/2) é em média 7 a 10 vezes mais rápido que o REST para esse tipo de tráfego de máquina para máquina.

### 5.3. Mensageria Assíncrona (RabbitMQ)
Para não onerar o banco de dados com buscas complexas, o Catalog Service publicará eventos no RabbitMQ (Exchange: `catalog.events`) sempre que o status quo mudar:
*   Evento: `AffiliationCreatedEvent` (Payload com dados do Salão, Profissional e Serviços).
*   *Quem escuta?* O **Search Service**, que pegará esse JSON e salvará/atualizará um grande documento no **Elasticsearch** para busca ultrarrápida (CQRS).

## 6. Validações e Regras de Negócio Core (TDD)
O pacote `core/` do Catálogo deverá conter testes unitários rígidos para as seguintes Invariantes de Domínio:
1.  **Validação de Horário:** Ao tentar adicionar um `WorkSchedule` para um profissional das 07h às 15h, se o salão só abre às 09h, o UseCase deve lançar `BusinessRuleException("Horário do profissional fora do expediente do salão")`.
2.  **Sobreposição de Horários:** Garantir que o dono do salão não cadastre duas grades conflitantes para o mesmo profissional no mesmo dia (ex: Segundas das 09h às 12h e Segundas das 10h às 14h).
de Domínio:** Pular para a **RFC-007: Booking Service**, que é o microsserviço que consumirá este gRPC para calcular a disponibilidade em tempo real e fazer o bloqueio no banco de dados para evitar o *Double-Booking*?
