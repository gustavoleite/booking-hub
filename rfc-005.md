# RFC-005: Tratamento Global de Erros e Exceções de Domínio no Auth Service

**Autor:** [Seu Nome/Sua Equipe]
**Data:** 24 de Março de 2026
**Status:** 🟢 Aprovada para Implementação
**Componente:** Auth Service
**Stack:** Spring Boot (`@RestControllerAdvice`), JUnit 5, Cucumber, Problem Details (RFC 7807)

## 1. Sumário Executivo
Esta RFC propõe a reestruturação do tratamento de erros no processo de Registro de Usuários do **Auth Service**. Atualmente, cenários de *E-mail Duplicado*, *Senha Fraca* e *Role Inválida* retornam um genérico `403 Forbidden`. O objetivo é criar **Exceções de Domínio** na camada *Core* e mapeá-las na camada de *Infrastructure* para códigos HTTP semanticamente corretos, acompanhados de testes unitários (TDD) e BDD.

## 2. Contexto e Motivação (Segurança e Semântica HTTP)
*   **E-mail já cadastrado:** Retornar 403 é incorreto. O correto é `409 Conflict` (indica conflito com um recurso existente). *Nota de Segurança:* Em sistemas ultra-críticos (bancos), evita-se dizer "email já existe" para prevenir *User Enumeration* (tentativa e erro para descobrir quem é cliente). Porém, para um app de agendamento, focar na usabilidade e informar o erro `409` é o padrão de mercado aceito.
*   **Senha Fraca:** O correto é `400 Bad Request`. A API deve informar explicitamente as regras da política de senhas para o usuário corrigir.
*   **Role Inválida:** O correto é `400 Bad Request`. O cliente enviou um enum que o sistema não reconhece.

## 3. Desenho da Solução (Clean Architecture)

A solução respeitará a regra de dependência: o *Core* lança exceções puras do Java, e o *Spring Boot* (Infra) as captura e traduz para HTTP.

### 3.1. Camada Core (Regras de Negócio)
Criaremos três exceções de negócio estendendo `RuntimeException`:
*   `EmailAlreadyExistsException`
*   `WeakPasswordException`
*   `InvalidRoleException`

A lógica no `RegisterUserUseCase` (desenvolvida via TDD) ficará assim:
```java
// core/usecases/RegisterUserUseCaseImpl.java
public void execute(User user) {
    if (userRepository.existsByEmail(user.getEmail())) {
        throw new EmailAlreadyExistsException("O e-mail informado já está em uso.");
    }
    if (!passwordPolicy.isValid(user.getPassword())) {
        throw new WeakPasswordException("A senha deve conter no mínimo 8 caracteres, uma letra maiúscula e um número.");
    }
    if (!Role.isValid(user.getRole())) {
        throw new InvalidRoleException("Perfil de usuário inválido. Valores permitidos: ROLE_CLIENT, ROLE_PROFESSIONAL, ROLE_OWNER.");
    }
    // ... segue fluxo normal
}
```

### 3.2. Camada Infrastructure (Spring Boot)
Utilizaremos o `@RestControllerAdvice` em conjunto com a especificação **Problem Details (RFC 7807)**, que já vem nativa no Spring Boot 3 (via `ProblemDetail`).

```java
// infrastructure/adapters/in/rest/GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(EmailAlreadyExistsException.class)
    public ResponseEntity<ProblemDetail> handleEmailExists(EmailAlreadyExistsException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
        problem.setTitle("Conflito de Dados");
        return ResponseEntity.status(HttpStatus.CONFLICT).body(problem);
    }

    @ExceptionHandler({WeakPasswordException.class, InvalidRoleException.class})
    public ResponseEntity<ProblemDetail> handleBadRequest(RuntimeException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, ex.getMessage());
        problem.setTitle("Dados de Entrada Inválidos");
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(problem);
    }
}
```

## 4. Estratégia de Qualidade (Testes)

### 4.1. TDD no UseCase (Testes Unitários em Milissegundos)
Garantimos que a regra de negócio dispara a exceção correta utilizando Mockito.

```java
@Test
void shouldThrowEmailAlreadyExistsException_whenEmailIsTaken() {
    // Arrange
    when(userRepository.existsByEmail("existente@teste.com")).thenReturn(true);
    User inputUser = new User("existente@teste.com", "SenhaForte123!", "ROLE_CLIENT");

    // Act & Assert
    assertThrows(EmailAlreadyExistsException.class, () -> {
        registerUserUseCase.execute(inputUser);
    });
}
```

### 4.2. BDD no Cucumber (Testes de Integração / Comportamento)
Atualizaremos o arquivo `register.feature` para cobrir os novos cenários de erro e validar os códigos HTTP corretos.

```gherkin
Funcionalidade: Registro de Usuário com Validações de Segurança

  Cenário: Tentativa de registro com e-mail já existente
    Dado que o e-mail "cliente@teste.com" já está cadastrado no banco de dados
    Quando eu envio uma requisição POST para "/api/auth/register" com este e-mail
    Então o status da resposta deve ser 409 CONFLICT
    E o corpo da resposta deve conter o título "Conflito de Dados"

  Cenário: Tentativa de registro com senha fraca
    Quando eu envio uma requisição POST para "/api/auth/register" com a senha "123"
    Então o status da resposta deve ser 400 BAD REQUEST
    E o corpo da resposta deve informar que a senha deve conter no mínimo 8 caracteres

  Cenário: Tentativa de registro com perfil (role) inválida
    Quando eu envio uma requisição POST para "/api/auth/register" com a role "ROLE_HACKER"
    Então o status da resposta deve ser 400 BAD REQUEST
    E o corpo da resposta deve informar os valores permitidos
```

## 5. Atualização das Documentações (Swagger e Postman)

### 5.1. Atualização do Swagger (OpenAPI)
Para refletir os novos retornos, atualizaremos as anotações no `AuthController`:

```java
@Operation(summary = "Registrar um novo usuário", description = "Cria conta para clientes, profissionais ou donos de salão.")
@ApiResponses(value = {
    @ApiResponse(responseCode = "201", description = "Usuário criado com sucesso"),
    @ApiResponse(responseCode = "400", description = "Dados inválidos (Senha fraca ou Role inexistente)", 
                 content = @Content(schema = @Schema(implementation = ProblemDetail.class))),
    @ApiResponse(responseCode = "409", description = "E-mail já cadastrado", 
                 content = @Content(schema = @Schema(implementation = ProblemDetail.class)))
})
@PostMapping("/register")
public ResponseEntity<Void> register(@RequestBody RegisterDTO dto) { ... }
```
