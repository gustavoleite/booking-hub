# RFC-001: Arquitetura e Implementação do API Gateway

**Autor:** [Seu Nome/Sua Equipe]
**Data:** 23 de Março de 2026
**Status:** 🟡 Em Revisão (Aberto para Comentários)
**Componente:** API Gateway (Edge Service)
**Stack:** Java 21+, Spring Boot 3.x, Spring Cloud Gateway (WebFlux / Netty)

---

## 1. Sumário Executivo
Esta RFC propõe a implementação de um API Gateway centralizado baseado no **Spring Cloud Gateway**. Ele atuará como o único ponto de entrada (Edge Service) para todos os clientes externos (Front-end/Postman) interagirem com o ecossistema de microsserviços do sistema de agendamento de beleza e bem-estar.

## 2. Contexto e Motivação
Adotamos uma arquitetura distribuída com 6 microsserviços (`Auth`, `Catalog`, `Booking`, `Review`, `Search`, `Notification`). Permitir que os clientes comuniquem-se diretamente com cada serviço geraria os seguintes problemas:
* **Acoplamento de Infraestrutura:** O cliente precisaria conhecer o IP/Porta de cada serviço.
* **Redundância de Código:** Todos os microsserviços teriam que implementar validação de token JWT e políticas de CORS de forma independente.
* **Superfície de Ataque:** Exporíamos rotas internas (como o serviço de notificação) para a internet.

## 3. Objetivos e Não-Objetivos

### Objetivos (O que o Gateway fará):
* **Roteamento Dinâmico:** Encaminhar requisições REST para o microsserviço correto baseado no prefixo da URL (ex: `/api/bookings/**`).
* **Offloading de Autenticação:** Interceptar chamadas protegidas, validar a assinatura matemática e expiração do JWT.
* **Mutação de Cabeçalhos:** Injetar o `User-Id` e `Roles` extraídos do JWT como cabeçalhos HTTP (ex: `X-User-Id`) para os microsserviços, poupando-os de processar o token novamente.
* **Observabilidade:** Gerar e injetar um `X-Correlation-ID` em todas as requisições para rastreamento distribuído nos logs.
* **CORS Centralizado:** Gerenciar as regras de Cross-Origin Resource Sharing em um só lugar.

### Não-Objetivos (O que o Gateway NÃO fará):
* **Lógica de Negócio:** O gateway será "burro" em relação aos dados. Não fará consultas a bancos de dados.
* **Geração de Tokens:** A emissão e renovação de JWTs é responsabilidade exclusiva do `Auth Service`.
* **Agregação Complexa de Dados (BFF):** Não faremos chamadas a múltiplos serviços para juntar o payload (usaremos o GraphQL em outro escopo no futuro, se necessário).

---

## 4. Desenho da Solução

O Spring Cloud Gateway é construído sobre o **Project Reactor (WebFlux)** e rodará no servidor **Netty** (não bloqueante e orientado a eventos), garantindo alta performance e baixo consumo de recursos estruturais para suportar milhares de conexões simultâneas.

### 4.1. Fluxo de uma Requisição de Agendamento
1. O cliente faz um `POST /api/bookings` com o header `Authorization: Bearer <jwt>`.
2. O servidor Netty recebe a requisição.
3. O **Filtro Global de Correlation ID** injeta um UUID na requisição para rastreabilidade.
4. O **Filtro de Autenticação (JWT Auth Filter)** valida a assinatura do token usando a Chave Pública RSA fornecida pelo Auth Service.
5. Se válido, o filtro extrai o `sub` (ID do usuário) e adiciona ao header interno `X-User-Id`.
6. O predicado de roteamento identifica que `/api/bookings/**` deve ir para a URI interna `http://booking-service:8080`.
7. A resposta do microsserviço faz o caminho reverso até o cliente.

## 5. Proposta de Configuração (Code Design)

Em vez de configurar as rotas via código Java, utilizaremos o `application.yml` parametrizável. Isso atende ao nosso requisito de portabilidade Docker-first.

```yaml
# application.yml do API Gateway
server:
  port: 8080

spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      globalcors:
        cors-configurations:
          '[/**]':
            allowedOrigins: "*" # Em prod, restringir para o domínio do front-end
            allowedMethods:[ "GET", "POST", "PUT", "DELETE", "OPTIONS" ]
            allowedHeaders: "*"
            
      routes:
        # 1. Rota Pública do Auth Service
        - id: auth-service-route
          uri: ${AUTH_SERVICE_URI:http://auth-service:8081}
          predicates:
            - Path=/api/auth/**
            
        # 2. Rota Protegida do Booking Service
        - id: booking-service-route
          uri: ${BOOKING_SERVICE_URI:http://booking-service:8082}
          predicates:
            - Path=/api/bookings/**
          filters:
            - JwtAuthFilter # Nosso filtro customizado que será criado no código

        # 3. Rota Mista do Catalog Service (GET público, POST/PUT privado)
        - id: catalog-service-route
          uri: ${CATALOG_SERVICE_URI:http://catalog-service:8083}
          predicates:
            - Path=/api/catalog/**
```

### 5.1. O Filtro Customizado de Autenticação (Esboço Java)
Para o `JwtAuthFilter` mencionado no YAML acima, criaremos uma classe implementando `GatewayFilterFactory`.

```java
@Component
public class JwtAuthFilter extends AbstractGatewayFilterFactory<JwtAuthFilter.Config> {

    @Autowired
    private JwtValidationService jwtValidationService;

    public JwtAuthFilter() { super(Config.class); }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> {
            ServerHttpRequest request = exchange.getRequest();

            // 1. Verifica se o Header Authorization existe
            if (!request.getHeaders().containsKey(HttpHeaders.AUTHORIZATION)) {
                return onError(exchange, "Missing Authorization Header", HttpStatus.UNAUTHORIZED);
            }

            String token = request.getHeaders().getFirst(HttpHeaders.AUTHORIZATION).substring(7);

            try {
                // 2. Valida matematicamente o token (Sem ir ao BD)
                Claims claims = jwtValidationService.validateTokenAndGetClaims(token);
                
                // 3. Muta a requisição enviando o ID do usuário de forma segura para os microsserviços
                exchange.getRequest().mutate()
                        .header("X-User-Id", claims.getSubject())
                        .header("X-User-Role", claims.get("role", String.class))
                        .build();

            } catch (Exception e) {
                return onError(exchange, "Invalid JWT Token", HttpStatus.UNAUTHORIZED);
            }

            return chain.filter(exchange);
        };
    }
    
    // Configuração base omitida para brevidade
    public static class Config {}
}
```

## 6. Alternativas Consideradas

* **AWS API Gateway:** Rejeitado. Embora seja serverless e nativo da AWS, adotar o Spring Cloud Gateway nos dá mais controle sobre a implementação, permite rodar 100% da infraestrutura localmente (via Docker Compose) para testes do Tech Challenge e demonstra domínio avançado no ecossistema Spring.
* **Netflix Zuul:** Rejeitado. É um projeto bloqueante (síncrono) e entrou em modo de manutenção. O Spring Cloud Gateway é a solução moderna (reativa) da Pivotal/VMware.
* **Kong API Gateway:** Excelente alternativa, mas exigiria aprender e manter scripts em Lua. Manter tudo em Java (Spring) unifica as competências técnicas da equipe.

---

## 7. Segurança e Performance

* **Latência:** Como não faremos chamadas de I/O em banco de dados dentro do Gateway, a latência adicionada por requisição deve ser inferior a **15ms**.
* **Observabilidade:** O Gateway exportará métricas em formato Prometheus para o `/actuator/prometheus`, permitindo monitorar picos de tráfego, erros HTTP 5xx e tempo de resposta diretamente num dashboard do Grafana.
* **Rate Limiting (Futuro):** Embora não implementado na V1 para economizar tempo, o Spring Cloud Gateway possui integração nativa com o **Redis** para implementar um limitador de requisições por IP (ex: 10 requisições/segundo no endpoint de login) com apenas 5 linhas de configuração, protegendo contra *Brute Force*.

## 8. Questões em Aberto (Open Questions para a Equipe)

1. **Gestão da Chave Pública (RSA):** O gateway precisa validar a assinatura do JWT. Devemos ler a chave pública estática de um arquivo de configuração/Environment Variable ou o Gateway deve baixar a chave pública do Auth Service na inicialização via um endpoint JWKS (JSON Web Key Set)?
    * *Recomendação do Autor:* Na V1, passar a chave pública via Variável de Ambiente (`RSA_PUBLIC_KEY`) no Docker Compose para simplificar.
2. **Tratamento de Erros Global:** Como vamos padronizar o JSON de erro do Gateway (ex: quando retorna 401 ou 404)? Seguiremos o padrão RFC 7807 (Problem Details for HTTP APIs)?
