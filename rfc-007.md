# RFC-007: Gestão de Ciclo de Vida (CRUD) das Raízes de Agregado do Catalog Service

**Autor:** [Seu Nome/Sua Equipe]
**Data:** 25 de Março de 2026
**Status:** 🟡 Em Revisão (Aberto para Comentários)
**Componente:** Catalog Service (Domínio Base)
**Stack:** Java 21, Spring Boot, Spring Data JPA, Flyway (PostgreSQL), MapStruct (para DTOs)

## 1. Sumário Executivo
Esta RFC propõe o design e a implementação dos endpoints REST, esquemas de banco de dados e Casos de Uso (Clean Architecture) para as operações de CRUD (Create, Read, Update, Delete) das duas Raízes de Agregado do Catalog Service: **Establishment** e **Professional**. Esta camada fundacional é pré-requisito para as futuras regras de precificação dinâmica, vínculos (Affiliations) e agendamentos.

## 2. Princípios de Design
* **Separação de Identidade:** O `ownerId` (Dono do Salão) e o `professionalId` (Profissional) são os mesmos UUIDs gerados pelo `Auth Service`. O API Gateway passará esses IDs via Header HTTP (`X-User-Id`), garantindo que um usuário só possa editar os próprios dados.
* **Soft Delete:** Entidades nunca serão fisicamente apagadas do banco de dados (comando `DELETE` SQL) para manter a integridade histórica de agendamentos e avaliações. Utilizaremos uma flag `active = false`.
* **Idempotência:** Requisições de atualização (PUT) serão desenhadas para serem idempotentes.

## 3. Modelagem de Dados Base (Flyway Migrations / PostgreSQL)

Antes do código Java, definimos o contrato do banco de dados relacional.

**Script V1__create_catalog_base_tables.sql**
```sql
-- Tabela de Estabelecimentos (Agregado: Establishment)
CREATE TABLE tb_establishments (
    id UUID PRIMARY KEY,
    owner_id UUID NOT NULL, -- Vem do Auth Service
    cnpj VARCHAR(14) UNIQUE NOT NULL,
    name VARCHAR(100) NOT NULL,
    description TEXT,
    phone VARCHAR(20),
    active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Tabela de Endereços (Value Object atrelado ao Establishment)
CREATE TABLE tb_addresses (
    establishment_id UUID PRIMARY KEY REFERENCES tb_establishments(id),
    street VARCHAR(150) NOT NULL,
    number VARCHAR(10),
    city VARCHAR(50) NOT NULL,
    state VARCHAR(2) NOT NULL,
    zip_code VARCHAR(10) NOT NULL,
    latitude DECIMAL(10, 8),
    longitude DECIMAL(11, 8)
);

-- Tabela de Horários Base do Salão (Value Object atrelado ao Establishment)
CREATE TABLE tb_default_business_hours (
    id UUID PRIMARY KEY,
    establishment_id UUID REFERENCES tb_establishments(id),
    day_of_week INTEGER NOT NULL, -- 1(Seg) a 7(Dom)
    open_time TIME NOT NULL,
    close_time TIME NOT NULL,
    UNIQUE(establishment_id, day_of_week)
);

-- Tabela de Serviços Base (Entidade Interna do Establishment - SEM PREÇO AINDA)
CREATE TABLE tb_provided_services (
    id UUID PRIMARY KEY,
    establishment_id UUID REFERENCES tb_establishments(id),
    title VARCHAR(100) NOT NULL,
    description TEXT,
    active BOOLEAN DEFAULT TRUE
);

-- Tabela de Profissionais (Agregado: Professional)
CREATE TABLE tb_professionals (
    id UUID PRIMARY KEY, -- Mesmo UUID do Auth Service
    name VARCHAR(100) NOT NULL,
    bio TEXT,
    avatar_url VARCHAR(255),
    specialties TEXT, -- Pode ser um JSONB ou CSV (ex: "Cabelo,Barba")
    active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## 4. Contratos de API (Endpoints REST)

### 4.1. Domínio: Establishment (Acesso: `ROLE_OWNER`)

#### A. Criar Estabelecimento (`POST /api/catalog/establishments`)
Cria o salão, o endereço e a grade de horários mestre em uma única transação (ACID).
* **Header Mocado do Gateway:** `X-User-Id: 123e45...`
* **Request Body:**
  ```json
  {
    "name": "Barbearia Vintage",
    "cnpj": "12345678000199",
    "description": "A melhor da cidade",
    "address": { "street": "Rua X", "city": "São Paulo", "state": "SP", "zipCode": "01000-000" },
    "businessHours":[
      { "dayOfWeek": 1, "openTime": "09:00", "closeTime": "18:00" },
      { "dayOfWeek": 2, "openTime": "09:00", "closeTime": "18:00" }
    ]
  }
  ```
* **Response (201 Created):** Retorna o ID gerado (UUID).

#### B. Listar Meus Estabelecimentos (`GET /api/catalog/establishments/my-salons`)
Busca todos os salões onde o `owner_id` bate com o `X-User-Id` do header. Retorna array simplificado.

#### C. Atualizar Estabelecimento (`PUT /api/catalog/establishments/{id}`)
Atualiza dados cadastrais. Regra de Segurança: O backend deve validar se o Salão `{id}` realmente pertence ao usuário logado (`owner_id == X-User-Id`). Se não, retorna `403 Forbidden`.

#### D. Inativar Estabelecimento (`DELETE /api/catalog/establishments/{id}`)
Faz o *soft delete* (muda `active` para false). Retorna `204 No Content`.

#### E. Gerenciar Serviços Base do Salão
*   `POST /api/catalog/establishments/{id}/services` (Adiciona um serviço ex: "Corte")
*   `DELETE /api/catalog/establishments/{id}/services/{serviceId}` (Inativa o serviço)

### 4.2. Domínio: Professional (Acesso: `ROLE_PROFESSIONAL`)

Como o `ID` do profissional é o seu próprio `User ID`, não precisamos passar o ID na URL para operações de escrita, evitando falhas de autorização (Insecure Direct Object Reference - IDOR).

#### A. Criar/Atualizar Perfil (`PUT /api/catalog/professionals/me`)
Funciona como um *Upsert* (Se não existe, cria; se existe, atualiza).
* **Header Mocado do Gateway:** `X-User-Id: 987f65...`
* **Request Body:**
  ```json
  {
    "name": "João Barbeiro",
    "bio": "Especialista em degradê e barba terapia há 5 anos.",
    "specialties":["Cabelo", "Barba", "Sobrancelha"],
    "avatarUrl": "https://s3.aws.com/bucket/joao.jpg"
  }
  ```
* **Response:** `200 OK`

#### B. Ler Meu Perfil (`GET /api/catalog/professionals/me`)

### 4.3. Consultas Públicas (Acesso: Público via Search/Gateway)
Qualquer pessoa (sem estar logada) pode ver os dados públicos:
* `GET /api/catalog/establishments/{id}` (Traz detalhes do salão, horários e serviços oferecidos).
* `GET /api/catalog/professionals/{id}` (Traz a bio e especialidades do profissional).

## 5. Arquitetura de Código (Use Cases - Clean Architecture)

Para manter o princípio SOLID, criaremos os seguintes *Use Cases* independentes no pacote `core/usecases/`:

1.  `CreateEstablishmentUseCase`
2.  `UpdateEstablishmentUseCase`
3.  `InactivateEstablishmentUseCase`
4.  `AddProvidedServiceUseCase`
5.  `UpsertProfessionalProfileUseCase`
6.  `GetEstablishmentDetailsUseCase` (Query)

### 5.1. Regras de Negócio e Invariantes (Para cobrir com TDD)

Os testes unitários desses Casos de Uso devem garantir as seguintes regras:
*   **CNPJ Único:** O `CreateEstablishmentUseCase` deve lançar `ConflictException` (409) se o CNPJ já existir no banco.
*   **CNPJ Válido:** Deve conter exatamente 14 dígitos numéricos (validação de formato).
*   **Validação de Horário:** O `closeTime` de um `BusinessHour` deve ser obrigatoriamente *depois* do `openTime` (Ex: Não pode abrir às 18h e fechar às 09h). Lança `BusinessRuleException` (400).
*   **Limite de Serviços:** Um salão deve ter no mínimo 1 serviço base cadastrado, e o nome do serviço não pode ser vazio.
