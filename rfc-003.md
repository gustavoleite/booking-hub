# RFC-003: Estratégia de Portabilidade (12-Factor) e Qualidade de Software (TDD/BDD/Testcontainers)

**Status:** 🟡 Em Revisão (Aberto para Comentários)
**Componentes Afetados:** API Gateway, Auth Service (e futuros serviços)
**Stack de Qualidade:** JUnit 5, Mockito, Testcontainers, Cucumber (BDD), k6, Docker

---

## 1. Sumário Executivo
Esta RFC define os padrões de infraestrutura e qualidade de software que devem ser implementados obrigatoriamente no **API Gateway** e no **Auth Service**. O objetivo é garantir que as aplicações sejam 100% portáveis entre o ambiente local (Docker Compose) e a nuvem (AWS ECS), além de estabelecer a pirâmide de testes exigida pelo projeto (TDD, Integração via Testcontainers e BDD).

## 2. Contexto e Motivação
Desenvolver "na máquina local" e depois ter problemas para fazer o deploy na AWS é um dos maiores riscos do projeto. Para mitigar isso, adotaremos os princípios do **12-Factor App**, externalizando todas as configurações. Além disso, o PDF do Tech Challenge exige alta cobertura de testes, integração contínua (CI) e testes não funcionais de carga. Precisamos de um padrão claro de como codificar essas validações.

---

## 3. Diretriz 1: Portabilidade e Configuração (Docker-First)

Nenhum microsserviço deverá conter credenciais, IPs ou portas *hardcoded* em seu código-fonte ou em seus arquivos de propriedades estáticos.

### 3.1. Uso de Variáveis de Ambiente no Spring Boot
Os arquivos `application.yml` devem utilizar a interpolação do Spring para injetar valores em tempo de execução, fornecendo *fallbacks* (valores padrão) para o ambiente local.

**Exemplo no Auth Service (`application.yml`):**
```yaml
spring:
  datasource:
    # Se DB_HOST não existir no SO, usa 'localhost'
    url: jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:auth_db}
    username: ${DB_USER:admin}
    password: ${DB_PASS:admin123}
  
rsa:
  private-key: ${RSA_PRIVATE_KEY_PATH:classpath:certs/private_key.pem}
```

### 3.2. Perfis de Execução (Spring Profiles)
Teremos pelo menos dois perfis bem definidos:
*   `application-local.yml`: Ativado ao rodar na IDE. Espera que a infraestrutura (Postgres) esteja rodando no `localhost` via Docker Compose.
*   `application-aws.yml`: Ativado no deploy (AWS ECS). As variáveis como `DB_HOST` serão injetadas pelo *Task Definition* do ECS apontando para um banco RDS. O container Docker gerado será exatamente o mesmo.

### 3.3. Imagens Docker Imutáveis
O `Dockerfile` de ambos os serviços usará *Multi-stage Build* para compilar e empacotar a aplicação em uma imagem JRE leve (ex: Eclipse Temurin Alpine), garantindo que a imagem testada no CI seja a mesma promovida para produção.

## 4. Diretriz 2: Estratégia de Qualidade e Testes

A implementação do Gateway e do Auth Service deve seguir rigorosamente a seguinte pirâmide:

### 4.1. Testes Unitários e TDD (Foco no Core)
No **Auth Service**, o pacote `core/` (onde reside a Clean Architecture) deve ser desenvolvido usando TDD.
*   **Ferramentas:** JUnit 5 e Mockito.
*   **Regra:** Não utilizar `@SpringBootTest` aqui. Os testes devem rodar em milissegundos.
*   **Exemplo:** Testar se o `AuthenticateUserUseCase` lança exceção `InvalidCredentialsException` quando a senha não bate com o hash.

### 4.2. Testes de Integração com Testcontainers
Para testar os adaptadores de banco de dados (`UserRepositoryImpl`), não usaremos banco de dados em memória (como o H2), pois ele não reflete o comportamento real de dialetos do PostgreSQL em produção.
*   **Ferramentas:** Testcontainers.
*   **Comportamento:** Ao rodar `mvn test`, o Java via Docker API fará o pull da imagem `postgres:16`, subirá um container efêmero, rodará as *migrations* do Flyway, executará o teste real de *insert/select* e matará o container.

**Exemplo de Setup (Auth Service):**
```java
@Testcontainers
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
public class UserRepositoryIT {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
    
    // ... testes reais acessando o DB
}
```

### 4.3. Testes BDD (Behavior-Driven Development)
Para testar os *Controllers* REST e a jornada do usuário final (exigência para facilitar comunicação com stakeholders), utilizaremos BDD integrado ao Spring Boot.
*   **Ferramentas:** Cucumber e REST Assured.
*   **Onde:** Nos pacotes `adapters/in/rest`.

**Exemplo de Cenário (`login.feature` no Auth Service):**
```gherkin
Funcionalidade: Autenticação de Usuário
  Como um usuário cadastrado
  Quero fazer login com meu email e senha
  Para obter um token de acesso aos serviços

  Cenário: Login bem-sucedido com credenciais válidas
    Dado que existe um usuário com email "cliente@teste.com" e senha "senha123"
    Quando eu envio uma requisição POST para "/api/auth/login" com estas credenciais
    Então o status da resposta deve ser 200 OK
    E o corpo da resposta deve conter um "accessToken" válido
```

### 4.4. Testes de Roteamento (API Gateway)
Para o Gateway, os testes devem garantir que as rotas configuradas no `.yml` funcionem e que o `JwtAuthFilter` barra requisições sem token.
*   **Ferramentas:** `WebTestClient` e **WireMock** (para simular respostas *mockadas* dos microsserviços de backend).

### 4.5. Testes Não Funcionais (Carga/Performance)
*   **Ferramenta:** k6 (scriptado em JavaScript).
*   **Alvo:** O API Gateway (`/api/auth/login`).
*   **Objetivo:** Garantir que o Gateway e o Auth Service suportam, por exemplo, 200 requisições simultâneas por segundo sem degradar o tempo de resposta acima de 500ms e sem estourar o limite de conexões do banco de dados (avaliando o pool do HikariCP).

## 5. Questões em Aberto (Open Questions para a Equipe)

1. **Gestão do Cucumber no CI:** Os testes BDD costumam demorar mais para rodar, pois sobem o contexto web completo do Spring.
Resposta: Devemos separar o *goal* do Maven, ou seja, rodar testes unitários em cada *commit*, e rodar BDD apenas nos *Pull Requests* para a branch `main` no GitHub Actions.
